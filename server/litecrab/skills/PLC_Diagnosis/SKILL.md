# PLC 问题诊断总调度入口

## 使用方式

本文件是LLM的总调度入口，提供功能清单、问题路由和统一总结要求。具体问题的原因分析、修复方法及执行流存放在references文件夹，一个文件对应一个问题分类。识别问题后必须先读取对应文件，再按执行流操作；不能只完成参数修改就宣布问题修复。

职责：LLM负责问题识别、原因分支选择和结果判断；`scripts/main.c` 根据参数调度具体功能；`scripts/asp/` 中的函数各实现一个请求。LLM通过main命令调用功能，不直接调用C函数。没有 `diagnose_communication` 命令。

统一闭环：**问题识别 → 原因分支 → 修复动作 → 参数修复验证 → 问题修复验证 → 结论**。失败、未知、未覆盖也是明确的结束状态，必须报告停在哪一步以及还缺什么证据。

用户已要求自动修复或“发现通信异常就修改频段”时，按执行流自动完成一次修复及两层验证，不重复索要已授权的参数或许可。用户只要求查询时执行只读部分并报告，不自行进入写入步骤。

## 可调用功能

以下功能通过 `exec_program` 直接启动Linux二进制，不经过命令解释器。`command`填写二进制文件名，`path`填写其工作目录，每个命令行参数必须作为`args`中的独立字符串；参数值按实际任务动态填写。

```json
{"command":"main","path":"skills/PLC_Diagnosis/scripts","args":["-o","<命令>","<参数名>","<参数值>"]}
```

每个命令内部自动登录并复用本进程会话，无须在每一步之前另行调用login。

| 命令 | 对应接口函数 | 功能与关键参数 | 结果用途 |
|---|---|---|---|
| `login` | `do_login` | 单独验证登录；通用认证参数 | 排查认证失败 |
| `get_cache_info` | `asp_get_cache_info` | 查询设备缓存/连通信息 | 辅助判断设备响应，不能代替通信问题验证 |
| `get_active_alarm` | `asp_get_active_alarm` | 查询活动告警；`--equip-id`可选，默认0=全部 | 识别问题、修复后复查 |
| `get_monitor_info` | `asp_get_monitor_info` | 读信号；`--equip-id 4099 --equip-type-id 33036 --para3 4 --para4 2` | 读取修复前后参数，频段为sigId=8201 |
| `get_history_alarm` | `asp_get_history_alarm` | 历史告警；`--equip-id 1 --page-index 1 --page-size 20` | 辅助分析历史，不用历史告警代替活动告警判定当前状态 |
| `set_freq_band` | main组合监控查询、`asp_set_freq_band`、监控查询 | `--equip-id 4099 --equip-type-id 33036`；默认当前Band+1，可选`--value`指定目标 | 自动读取当前值、计算下一Band、写入、读回验证 |

通用参数：`--base-url/--user/--password/--langlist`；默认地址为 `https://192.168.8.10`，认证凭据由`exec_program`的最小子进程环境提供，禁止放入Tool参数；报告中不展示凭据。`--output <文件>`保存最后一次请求的原始响应，不保存整条执行流。

历史告警默认全部设备、最近365天、第1页20条；可指定 `--start-time/--end-time`（`YYYY-MM-DD-HH-mm-ss`）、`--alarm-level 0|1|2|3|255`（255全部）、`--sort-type 0|1`、`--sort-field 0|1`。

### 统一结果解析

1. 保存命令退出码。每条命令只输出一个归一化JSON对象，不再输出完整URL和原始ASP `body`，也不需要二次解析字符串形式的响应体。
2. 通用字段为 `schema_version/operation/success/exit_code/transport/business/query/data/warnings/error`；只信任实际存在的字段，不把缺失字段推断为成功。
3. HTTP成功仅代表传输成功。命令已在本地检查接口业务码和目标数据，并通过 `success/exit_code/business/error` 返回综合结果；LLM仍需结合任务步骤判断是否满足闭环条件。
4. `get_active_alarm` 在 `data.alarms` 返回本次查询范围内的活动告警核心字段。每条告警通过 `topCauses` 最多返回3组按接口原始顺序配对的 `reason/repair`；`cause_repair_total_count` 是原始组数，`cause_repair_truncated` 表示是否省略了第4组及以后内容。完整 `description/subReasonList` 不进入LLM上下文。
5. `get_monitor_info` 在 `data.devices[].signals[]` 返回本次信号组实际查询到的全部信号核心字段，不固定只返回8201。枚举值已归一化为可选的 `displayValue`；`returned_signal_count/missing_signal_ids/truncated` 说明结果完整性。当前C001从其中查找8201并使用 `sigValue/displayValue` 判断频段。
6. `get_history_alarm` 在 `data.alarms` 返回当前页告警核心字段，并通过 `total_count/returned_count/truncated` 说明分页情况。历史告警只作辅助证据，不代替活动告警。
7. `set_freq_band` 将修复前读取、计划、写入响应、读回和参数验证合并为一个JSON，检查 `before/planned/write/after/verification`。成功要求 `write.accepted=true`、`verification.readback_matches=true`、`verification.parameter_result="success"` 且进程退出0。
8. `get_cache_info` 的实机字段契约尚未确定，当前仅返回响应类型、字节数和 `schema_known=false` 警告，不把原始缓存内容发给LLM，也不把它作为通信修复判据。

完整字段定义和示例记录在仓库维护文档 `docs/plc/plc_llm_tool_output_filtering.md`；执行本Skill无需另行读取该文档。

退出码：0成功；1参数错；2本地错；3网络错；4HTTP或接口响应错误；5登录失败；6当前频段无效、无下一频段或读回失败。只读查询遇瞬时网络故障可重试一次；写入失败或响应不明时先只读核实，不重试自动递增写入。

## 推送告警入口检查（轮询与订阅共用）

收到告警监控传入的结构化消息（包含“告警ID、设备ID、告警序列号、告警时间”，并要求使用 PLC_Diagnosis）时，必须先执行 `get_active_alarm`，确认归一化结果满足 `success=true`、`exit_code=0` 且 `data.alarms` 为数组，再将消息字段还原为 `almid + equipid + seqno + localtime`，逐项核对本次推送告警是否仍在 `data.alarms` 中。推送内容是监控从 ASP 响应中提取的白名单摘要，只作为待核验证据，不能代替这次查询，也不能假定未传入的原始字段值。

- 四个字段完全匹配且告警仍活动：仅针对匹配项进入下方问题调度及已授权修复。
- 活动列表不再包含该项：报告“推送告警已失效，本次未执行修复”并结束，不得拿列表中的其他告警替代本次目标。
- 查询失败，或推送/查询结果缺少任一身份、序列或发生时间字段：报告入口检查无法完成，不执行任何写入。
- 设备和告警相同但 `seqno` 或 `localtime` 不同：视为另一次发生，不得当作原推送仍然有效。

在最终总结的“问题证据”中同时记录推送的 `localtime` 与重新查询的匹配结果，不输出凭据。

## 问题调度

1. 根据用户描述和已取得的证据识别问题分类。
2. 从下表选择对应文件并读取，只加载当前问题需要的文档。
3. 按该文件的执行流逐步判断和调用功能，完成参数修复验证及问题修复验证，遵守该问题的次数上限和停止条件。
4. 无论成功、失败、未发现问题或提前停止，都进入下方“最终总结”，输出一份完整总结后结束。
5. 同时涉及多个已支持问题时分别读取对应文件、分别保留证据，最后合并成一份总结，逐个报告两层验证结果。未匹配任何已支持分类时说明未覆盖，不套用通信异常修复动作。

| 问题编号 | 分类与触发描述 | 必须读取的执行指南 | 当前已实现原因 |
|---|---|---|---|
| P001 | 通信异常：通信失败、通信中断、设备离线等；是否修复由活动告警及分支条件决定 | [通信异常](references/通信异常.md) | C001：网络频段不匹配 |

当前其他问题和通信异常的其他原因尚未实现。路由到P001不等于根因已确认为频段，原因判断和闭环结论以对应文档及实际验证为准。

## 最终总结（必做）

每次任务结束必须向用户输出一份总结，包括正常完成、只读查询、未发现问题、未覆盖问题、失败和提前停止。多问题任务合并成一份总结。总结不能省略，也不能只返回原始JSON。保留以下字段：

告警监控触发的任务使用单向投递，最终总结由 Agent trace 保存，不回传给监控模块；这不改变本 Skill 必须生成完整总结的要求。

- **问题/分支**：例如P001通信异常 / C001网络频段不匹配（当前待验证原因）。
- **问题证据**：修复前目标告警及设备；未发现或查询失败需明确。
- **执行记录**：实际调用及退出码、关键业务码；未执行的动作不写成已完成。
- **参数修复结果**：修复目标设备、原Band/接口值→目标值→读回值；成功/失败/未知/未执行。
- **问题修复结果**：告警复查证据；本次复查已消除/仍存在/未知/未发现问题。
- **闭环结论与下一步**：依据对应问题文档的结果矩阵，说明完成或停在哪一步；禁止凭参数修改成功宣布通信恢复。

不输出密码、Cookie或token。若只读诊断结束，明确“本次未修改参数”。

## 后续扩展约定

新增通信异常原因时，在references/通信异常.md的P001下增加C002等分支，明确该原因的识别证据、选择优先级、修复功能与两层验证条件；不能把多个原因的修复动作全部执行一遍。

新增其他问题时，在references/下新建以问题分类命名的文件，例如references/<问题分类>.md，并在本入口的问题调度表增加P002等条目及实际文件链接。不要创建尚未实现的占位流程。每个问题文件按以下结构编写：

1. 问题定义和命中证据。
2. 输入参数及目标设备映射。
3. 已实现原因分支、判定条件和分支选择规则。
4. 每步准确命令、响应字段、成功/失败时的下一步。
5. 修复动作、次数上限及停止条件。
6. 参数修复判据与问题修复判据，分别给出。
7. 双层验证结果和闭环报告。

仅描述“待支持”的原因/问题不自动视为已有修复能力。需要新接口时先实现对应asp函数及main调度，再把准确用法加入可调用功能表和问题流程。
